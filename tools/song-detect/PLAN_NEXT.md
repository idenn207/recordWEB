# song-detect 개선 계획 (blind9 자체 검수 기반, 2026-10-27)

> 근거: `data/review/blind9/audit/` 의 g1~g4.json(메모 145행 검수), regression.json(회귀 191행), loso.json / loso_signals.json / loso_combo.json(일반화 측정), 조사 4건(R1~R4).
> 이 문서는 읽기 전용 분석의 결과이며 코드와 기존 데이터는 바꾸지 않았다. 구현은 4절 계획대로 다음 작업에서 한다.

## 0. 지난 처리의 문제 (먼저 인정)

지난 처리(HANDOFF 25절)는 사용자 판정 L/N/B 와 수치 규칙(tstd, speech, 등록부)만 맞췄다. 메모에 적힌 곡 길이, 화면, 실제 시작/종료 시각을 검증하지 않았고, "N 이 안 나온다"는 결과의 대부분이 규칙이 아니라 `known_negatives` 등록 덕이었다(1절 확인). 이번 검수는 메모를 점검 항목으로 쪼개 NAS 프레임, 스펙트로그램, 0.25초 단위 rms, 점수 캐시로 직접 대조한 것이다.

한계: 모든 검수는 파형, 점수, 프레임 이미지로 했고 귀로 듣지는 못했다. 메모의 "완곡 여부", "호흡", "가사 구간" 같은 청취 판단은 `unverifiable` 로 남겼다.

## 1. 자체 검수 결과 요약

### 1.1 점검 항목 집계 (145행, 점검 318건)

| 구간 | 행 | pass | fail | unverifiable |
|---|---|---|---|---|
| g1 (1~36) | 36 | 59 | 9 | 6 |
| g2 (37~72) | 36 | 44 | 17 | 6 |
| g3 (73~110) | 38 | 66 | 35 | 17 |
| g4 (111~145) | 35 | 48 | 9 | 2 |
| 합계 | 145 | 217 (68%) | 70 (22%) | 31 (10%) |

- 메모의 사실 주장(화면 종류, 곡 길이, 시각)은 대체로 맞았다. 사용자 메모가 틀린 것으로 확인된 건 없고, 재현이 안 된 것은 3건(18의 "1분 끊김", 22, 82)이며 이 셋은 사용자에게 시각을 되묻는다(5절).
- fail 70건은 대부분 "우리 파이프라인이 메모 기준을 못 맞춤"이다. N 행의 fail 은 클립이 잘못된 게 아니라 "등록부 없이는 규칙이 못 잡음"이라는 뜻이다. 쌍으로 중복된 행(v2/v3 stale 쌍)이 많아 고유 곡 수는 104곡이다.

### 1.2 실패 패턴 순위 (행 번호, 쌍 포함)

1. **N 이 규칙이 아니라 등록부로만 막힘**: 가장 큰 문제. 수치는 1.4절. 행 1~13, 15~17, 27~33, 37~43, 72~81, 83, 84, 87, 88, 90~94, 97~104, 106~110.
2. **끝이 곡 중간/MR 끝 전에 잘림** (18행): 18(19.5초), 20/21(150초), 22(정답 불명), 25/26(99.5초), 53/54(마지막 구절), 63(약 10초), 65(허밍 아웃트로 3.2초), 70/71(MR 위 멘트), 61/62(감쇠 꼬리가 컷 밖), 136/137, 141/142. 82 는 오디오상 재현 안 됨.

7. **회수 가능한 부분 라이브가 통째 등록으로 막힘**: 33(앞 60초 BGM+멘트 뒤 MR 라이브 157초, 오디오 음량 단차가 사용자 01:00 과 0.5초 이내 일치).

### 1.4 N 이 등록부로만 막히는 비율 (LOSO, `loso.json`)

blind9 고유 N 55곡. 등록부(known_negatives)와 같은 방송/스트리머 풀을 제외하고 현재 규칙을 재현한 결과:

| 조건 | 완성본 노출(review) | weak(완성본 미생성) | drop |
|---|---|---|---|
| 현재(등록부 포함) | 0 | 0 | 55 |
| 등록부 제외 / 방송 제외 / 스트리머 제외 | 23 (42%) | 22 (40%) | 10 (18%) |

- 등록부 없이는 55곡 중 10곡(18%)만 규칙으로 drop 된다. review 로 새는 것이 23곡(42%), weak 22곡은 임계 25 가 N 분포를 보고 정한 값이라 일반화 근거가 약하다. "등록부로만 막힘"은 45/55(82%, weak 포함) 또는 23/55(42%, 노출 기준).
- 새는 유형(등록부 제외, review 노출/유형 N): 타 스트리머 같이보기 8/10, 자리비움 BGM 4/9, 잡담 중 BGM 3/5, 게임 OST 2/6, 리듬게임 2/8, 따라 부르기 1/3, 커버 같이보기 1/4, GTA 노래방 1/9, 같이 듣기 1/1. weak 포함하면 거의 모든 유형이 샌다.
- 다른 세트는 훨씬 낫다: blind5 N 16 중 노출 0(weak 2), blind6 N 3 중 0. 의존이 큰 것은 blind9 에서 처음 나온 유형(같이보기, 게임, 자리비움)이다.
- 라이브 쪽도 마찬가지다: blind9 auto 27 -> 0, blind6 auto 27 -> 0(방송/스트리머 제외). auto 는 거의 전부 승인 목록 겹침이 만든다. 스트리머 제외 시 likely 재현율 5/49(정밀 5/7). 새 방송에서는 review 가 다시 크게 늘어난다.
- 새 장면 풀 제외 시 라이브 손실: blind5 V15(D1 과 같은 곡), blind78 7C1/7C2. 라이브 보호에 풀 의존도 있다.

### 1.5 등록부 없이 쓸 수 있는 신호 (loso_combo, 표본 내 선택의 낙관 포함)

| 조합 | 누수 N / 75 | 손실 라이브 / 88 |
|---|---|---|
| 기존 규칙만 | 24 | 0 |
| + bursts_per_min | 9 | 1 |
| + bursts + sing_std | 6 | 2 (V21, V06) |
| + bursts + sing_std (임계 여유 x1.1) | 6 | 1 (V21) |
| + bursts + sing_std + moving_frac (x1.1) | 5 | 1 (V21) |

- 남는 누수는 GTA 4003(콘서트), 나나 15067(웹페이지 레이아웃), 따라 부르기 18197, 자리비움 17386, 7A 이며 audit 이 "신호 없음"으로 지목한 곡과 일치한다.
- audit 이 개별로 측정한 신호: 밝은 픽셀 비율(웹 레이아웃 1/28/29 가 0.84/0.33/0.31 대 라이브 최대 0.17), 곡 중앙값 dBFS 가 말소리보다 8dB 이상 낮음(N 23/55 포착, 라이브 손실 0, 최저 -4.0dB), 키프레임 차분 중앙값 < 6(N 12/71, 라이브 0/137, 키프레임 간격에 민감: 103 은 5.9 대 20.6), Speech>0.3 프레임 비율 >= 0.10(N 35/75, 라이브 1/70). 모두 3~4 스트리머 표본이고 임계가 N 으로 맞춰졌다.

### 2.2 하지 말 것 (비용 대비 효과 낮음 또는 근거 부족)

- **Demucs 분리를 전 후보에 적용**: CPU 로 곡당 수 분(미측정)이고, 분리기는 보컬과 게임 음성을 구분하지 못한다. 유효성은 20~30곡 표본으로 확인된 뒤에만.
- **Whisper/WhisperX 가사 정렬을 판정에 사용**: 한국어/일본어 가창 성능을 확인 못 했고 전주/간주 환각 위험(LyricWhiz 계열 지적)이 있다. 끝 early 9곡의 "끝 뒤 가사 존재 여부" 소표본 진단 용도로만.
- **새 분류 모델 학습, 가수 식별(ECAPA 대체)**: 정답 104곡으로는 과적합. ECAPA 실패는 원인 분해(말-말, 말-노래, 분리 후 노래-노래 AUC) 전에 모델을 바꾸는 것이 관성이다.
- **Snorkel 식 약한 감독, Confident Learning**: 104곡에서는 통계적 의미가 없다. 정렬 도구 이상의 가치가 없어 보류.
- **Dagster/DVC 도입**: 개념만 차용하고 의존성은 추가하지 않는다.
- **상용 클립 서비스, Twitch 하이라이트 문헌, 채팅 신호**: 목표가 다르고(스트리머 본인 MR 라이브, 경계 정밀) 채팅 수집 여부도 미확인. 근거 없는 추정이라 제외.
- **SSM novelty 로 경계 탐색**: 오류 규모(1~수십 초)와 맞지만 partly 근거이고 이득이 불확실. 3절의 후보 경계 방식이 안정된 뒤 소표본(끝 early 9곡)으로만 시험.
- **임계값 단독 이동으로 다음 N 막기**: 8/9(tstd 34.0 대 임계 34.5), 99(blk 0.093 대 0.10), 114(blk 0.508 대 0.50)처럼 N 이 임계 바로 밑에 걸려 있다. 임계를 옮기면 과적합이다.
- **detect gap_s 20 -> 30 / E1 grace 확대를 GPU 재탐지로**: GPU 금지 조건이고 후보가 급증(병합 대상 400개 이상)하므로 점수 캐시 기반 병합 시험이 끝나기 전엔 보류.

### 2.3 이번 조사로 알게 된 것이 우리 규칙에 주는 의미

- 후처리 파라미터(최소 지속, 최대 틈)는 방송 음악/말 분할 문헌에서 훨씬 작은 값(0.4~3.4초)이다. 우리 gap_s=20 은 곡 병합이라 다른 문제이지만, 간주 병합은 "틈 길이 하나"가 아니라 (틈 길이, 간주 중 Music 연속, 말 없음, 병합 후 길이 상한)의 조합 조건이 필요하다.
- 끝 여유/페이드 1초는 외부 근거가 없다. 청취 A/B(10곡 이하)로만 결정한다.

## 3. 하네스/구조 변경안

핵심은 "규칙을 한 번에 고쳐 판정이 맞았는지 보는 구조"에서 "변경마다 승인 곡 보호, 메모 대조, 일반화 측정이 자동으로 나오는 구조"로 바꾸는 것이다.

### 3.1 중간 산출물 단계화 (증거를 쌓고, 결정은 마지막에)

- 현재 단계: wav + scores.npy(원신호) -> detect/refine(후보) -> snap/finalize(경계 규칙) -> scene/route(등급) -> make_final(클립). 문제는 snap 이후 단계에서 경계가 누가 얼마 움직였는지가 카드에 남지 않는다(`why_snap=None`)는 점이다. 그래서 47/48 의 성공도 규칙 귀속은 추정이었다.
- 변경: 카드에 `stages`(detect, refine, snap, 규칙별 {name, before, after}, final)와 규칙 버전/입력 해시를 기록한다. 경계 규칙은 경계를 바로 덮어쓰지 않고 `candidates:[{rule, start|end, shift, evidence}]` 를 남기고, 적용 여부는 정책이 정한다(예: 새 규칙 S3/E1b/E4/E5 는 auto 에 적용 금지, B/review 후보 경계 전용. 승인 L 곡은 변경 금지).
- 이유: g1 의 S3 는 20번은 고치지만 승인 라이브 5곡의 승인 시작(음악 시작보다 15~25초 늦음)과 충돌했다. g2 의 S3 는 44/53 은 고치지만 #45(L, -15.5초), #47/#48, #60 을 퇴행시켰다. 규칙이 서로 다른 정답 기준과 부딪힐 때 "누가 이기는가"를 카드와 정책으로 분리해야 한다.
- 이미 있는 것: `experiments/audit_engine.py` 가 규칙을 끈 v3 와 v4 를 실제 json 과 0.06초 안에서 재현한다. 이 엔진이 shadow 실행의 기반이다(현재 untracked 이므로 커밋 필요).

### 3.2 판정 데이터 -> 규칙/모델

- labels.json 메모를 `expectations.json`(곡별 길이, 시작/끝 시각, 화면 유형 tag, 가창자, 청취가 필요한 항목)으로 구조화한다. 이미 loso 쪽에 N 유형 tag(afk_bgm, gta_karaoke, other_live_watch 등 9종)가 있으니 그것을 정식 필드로 올린다.
- `known_negatives` 의 의미를 재정의: 목적은 "규칙이 못 잡는 N 의 최후 보루"이고 지표는 "등록부 없이 노출되는 N 수"다. 등록으로 문제가 사라졌다고 보고하지 않는다.
- 학습은 하드 규칙(곡 길이 125~340초, 앞 5분, known_neg 겹침)은 그대로 두고, 소수 특징(1.5절 신호)을 강한 정규화 로지스틱 또는 단순 AND 규칙으로 결합하며 LOGO 로만 평가한다.

### 3.3 회귀 게이트 (승인 곡 이탈 0)

- golden set = approved.json 의 L(boundary_ok=True) + 재생목록 위치 정답 + 숫자 정답이 있는 B(47, 48, 60 등). 현행 v4 경계를 `golden_v4.json` 으로 동결.
- 게이트 조건: 시작/끝 이동 > 2초, 클립 길이 변화 > 3초, 곡 사라짐, 등급 하락, 이웃과 겹침 중 하나라도 있으면 이탈. 이탈 곡은 목록(곡, 규칙, 이동량, 정답 오차 전/후)으로 출력하고, 의도한 개선은 화이트리스트에 사유와 함께 명시해야 통과한다.
- regress_snap 은 "이동 수"만 셌다. 게이트는 "승인 곡이 움직였는가와 정답에 가까워졌는가"를 센다. audit_regress.py 가 이미 이 기능의 원형이다.

### 3.4 LOSO/LOGO 평가 의무화

- 임계/신호/풀 선택은 그룹(스트리머 x 방송일) 제외로 하고, 보고에는 항상 (a) hold-out 라이브 손실, (b) N 노출률(등록부 제외), (c) 새 스트리머 첫 곡 review 비율, (d) 부트스트랩 구간을 넣는다. 점추정만 적지 않는다.
- 표본 내 수치(likely 91% 등)는 "과적합 참고값"으로 라벨링한다.

### 3.5 사람에게 보여줄 후보 선택

- 목표: 사용자 검수 최대 10곡. 후보 = 규칙 변형 위원회의 경계 분산 상위, likely 점수 임계 근처, 새 유형/새 스트리머(밀도 가중). 이미 판정한 유형은 군집 대표 1곡만 묻고 전파한다(같은 방송 같이보기 9행, 나나 게임 10행처럼 군집이 뚜렷함).
- 평가용 풀은 불확실도로 뽑은 라벨과 섞지 않고 별도 유지한다.

### 3.6 자체 검수 도구 상시화 (메모 -> 점검 항목 -> 자동 검증)

점검 항목을 종류로 나눈다.

| 종류 | 예 | 자동화 |
|---|---|---|
| 시각/길이 | "00:19 부터", "5분 정도", "03:46 종료" | 자동: 경계 오차, 길이 오차 (mir_eval 식 hit) |
| 오디오 통계 | "멘트 없음", "말이 간헐", "BGM 만" | 자동: Speech 프레임 비율, 말소리 대비 상대 음량, 버스트 수 |
| 화면 | "같이보기", "노래방", "게임 HUD", "대기화면" | 반자동: 레이아웃 신호(밝은 픽셀, 프레임차, 프로브) + 프레임 이미지를 직접 확인 |
| 청취 | "완곡 여부", "호흡", "1절/2절" | 자동 불가: 사람 확인, unverifiable 로 기록 |

매 변경마다 이 점검을 전/후로 돌려 "메모 대비 통과 수"를 변경 보고의 첫 표로 둔다. L/N/B 판정 일치만 보고하지 않는다.

### 3.7 변경 완료 기준 (definition of done)

1. golden gate 이탈 0(또는 화이트리스트 사유 명시).
2. 메모 감사 표 전/후(hit@0.5/3/10, 길이 오차).
3. LOGO 표(라이브 손실, N 노출률).
4. 이동한 모든 경계 목록과, 그중 정답 없는 큰 이동은 프레임/스펙트로그램을 직접 본 소견.
5. 이 네 가지가 나온 뒤에만 사용자에게 확인을 요청한다.

- 성공 기준: 방송 단위 LOGO 에서 N 노출 23/55 -> 10/55 이하, 승인 107곡 라이브 손실 0, 신호별 단독 AUC 와 조합 이득 보고.
- 위험: 3~4 스트리머 표본, 임계가 N 으로 맞춰짐, 키프레임 간격 민감. 라이브 손실 1~2건이 이미 나타남(V21, V06).
- 이후로 미루는 이유: LOGO 도구(P4)가 있어야 평가가 의미 있고, 오디오 신호들은 서로 중복(speech, bursts, sing)되어 조합을 한 번에 평가해야 한다.

**P7. 사람 후보 선택(최대 10곡)과 군집 전파**
- 작업: 규칙 변형 위원회의 경계 분산 + likely 임계 근처 + 새 유형 우선. 같은 방송 같은 군집은 대표 1곡.
- 성공 기준: 사용자 지적 곡(끝 early 9곡 등)이 상위 10에 들어오는 precision@10 이 무작위 10 대비 2배 이상.
- 이후로 미루는 이유: 규칙 변형이 P2/P5 로 안정된 뒤에 의미가 있다.

**P8. 소규모 가치 확인 실험 (선택)**
- 작업: 원곡 지문(재생목록 곡 한정), Whisper 로 끝 early 9곡의 끝 뒤 가사 유무, SigLIP 프로브 GroupKFold, 곡 길이 prior, 합성 ducking 평가.
- 성공 기준: 각 실험이 기존 신호로 못 가른 N 또는 경계 오류를 추가로 N개 이상 설명할 때만 채택. 채택 기준 미달이면 폐기하고 기록.
- 이후로 미루는 이유: 비용 대비 가치가 불확실하고(partly/unverified), P1~P4 의 평가 도구가 있어야 채택 여부를 정할 수 있다.

단계화(stage manifest, 입력 해시 기반 stale 판정)는 P3 의 카드 `stages` 와 규칙 버전 기록으로 최소 형태만 도입하고, 해시 기반 자동 재실행은 재생성 593초 + 인코딩 2127초의 비용이 실제 병목이 될 때 검토한다(지금은 병목이 아님).
